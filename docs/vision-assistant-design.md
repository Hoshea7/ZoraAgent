# 视觉助手设计

> 状态：v2。v1 附件链路已实现并在 main 运行；v2 增量（路径输入源、定位升级）待实施。
> 日期：2026-08-17
> 取代：[archive/design/vision-relay-design.md](./archive/design/vision-relay-design.md)（v1，2026-08-11 定稿）

## 目标

视觉助手为不支持原生图片输入的主模型提供独立视觉模型，定位是 text-only 主模型的眼睛：主模型在任何位置遇到图片，都能通过它看到。

图片有三条来源，全部覆盖：

1. 对话框上传的图片附件（attachmentId）。
2. 本机路径图片：用户在消息中直接给出路径，或 Agent 通过文件工具（find、ls、grep、Read 拦截提示）发现的图片文件。
3. Agent 自己产出的图片：生成类工具（生图、截图、渲染）落盘的产物，主模型可对产出物做质量检查。

支持图片的主模型继续使用 Runtime 原生 Read，不经过视觉中转。

设置页只展示两项：启用视觉中转、选择视觉模型。视觉模型从已经配置的模型中选择，复用对应 Provider 的地址、协议和密钥。启用开关的描述明示外发范围：开启即授权将图片发送给所选视觉模型。

## 模型图片能力

图片能力有三个状态：

| 状态 | 语义 |
| --- | --- |
| `supported` | 已确认模型支持图片输入 |
| `unsupported` | 已确认模型不支持图片输入 |
| `unknown` | 当前没有足够信息确认 |

判定顺序：

1. 用户对当前 Provider 和模型设置的能力覆盖。
2. Zora 内置的已确认模型表。
3. Pi 模型目录中相同完整 modelId 的全部记录。任一 Provider 记录包含 `image` 输入即判定为 `supported`；全部精确记录均仅支持文本时判定为 `unsupported`。
4. 没有精确记录时判定为 `unknown`。

模型能力由完整 modelId 决定。相同 modelId 在任一中转 Provider 被确认支持图片后，其他 Provider 下的同名模型也按支持图片处理。用户覆盖按 Provider 保存，用于处理实际端点与标准模型能力不一致的情况。

视觉模型候选包含模型配置中全部已启用 Provider 的已配置模型。能力识别结果不限制用户选择，选择的模型能否处理图片由实际调用结果决定。

模型配置页提供折叠的图片能力识别设置。默认使用自动识别，用户只在识别结果不准确时选择支持图片或不支持图片。视觉助手页不展示能力表。

## 运行决策

每次 Agent Run 开始时解析一次主模型图片能力和视觉助手开关，生成不可变的 `VisionRunContext`。附件投影、工具注册和 Read 约束共用该上下文。

| 视觉助手 | 主模型能力 | 当前图片附件 | Inspect Image |
| --- | --- | --- | --- |
| 关闭 | 任意 | 保留普通附件引用和运行时路径，不增加图片工具指令 | 不注册 |
| 开启 | `supported` | 注入 attachmentId、运行时路径和一次性 Read 指令 | 不注册 |
| 开启 | `unsupported` | 只注入 attachmentId 和一次性 Inspect Image 指令 | 注册 |
| 开启 | `unknown` | 只注入 attachmentId 和一次性 Inspect Image 指令 | 注册 |

历史图片只投影文件名和 attachmentId，不重复注入 Read 或 Inspect Image 指令，也不包含图片字节和绝对路径。

定时任务和记忆任务不注册 Inspect Image。子 Agent、桌面会话与飞书会话使用相同的模型能力和视觉中转规则。

## 工具与权限

Inspect Image 的规范名称为 `mcp__zora_vision__inspect_image`，Claude 与 Pi 使用同一份工具定义。

Inspect Image 接受两种输入源，二选一：

| 输入源 | 参数 | 适用场景 | 权限 |
| --- | --- | --- | --- |
| 会话附件 | `attachmentId` | 用户在对话框上传的图片 | Ask 权限模式下自动允许 |
| 本机路径 | `path` | 用户直接给出图片路径，或 Agent 通过文件工具发现、产出的图片文件 | Ask 权限模式下自动允许，与 Read 同权 |

两条输入源共用同一条处理管线：格式校验、规范化、视觉中转请求。`attachmentId` 由附件资源模块解析；`path` 直接读取本机文件，文件头 sniff 判定图片格式，不信任扩展名。`path` 不存在或不可读时返回 `VISION_FILE_NOT_AUTHORIZED`。

`path` 与 Read 同权的理由：ask 模式下 Read 读取任意本机路径本来就自动放行，文件内容进入上下文即发送给主模型 Provider。图片经视觉中转发送给用户自己配置的视觉 Provider，属于同一性质的动作，外发面没有扩大，只是多了一个同样由用户配置的接收方。如果给 `path` 单独加每次审批，会出现 Read 任意文件不用确认、看一张图片反而要确认的矛盾体验。

外发授权在设置页完成：启用开关的描述明示开启即授权将本机图片发送给所选视觉模型，用户在有心智上下文的位置做一次性决定，质量高于在审批弹窗里看到一个孤立路径时的仓促判断。

Read 只在视觉助手开启且主模型为 `unsupported` 或 `unknown` 时拦截图片文件。拦截依据文件签名判断：已登记为会话附件的图片提示使用 attachmentId；未登记的本机图片直接提示使用 Inspect Image 的 `path` 参数，不再要求先登记为会话附件。文本、代码、PDF 等非图片文件不受影响。视觉助手关闭时不增加此限制。

不采用 Pi 原生软路径（Read 返回省略提示、传输层丢弃图片块）：图片仍会被完整解码后丢弃，浪费计算；Claude 侧 Read 返回图片块后 text-only 端点请求会整体失败。保留拦截并给出正确指引是两个 Runtime 上都成立的做法。

工具描述需要让模型在无人工指引下自主发现这条链路，说明三点：当前模型无法直接查看图片，遇到本机图片路径或会话附件 attachmentId 时使用本工具；每次发送一张图片和一条聚焦的观察问题给用户配置的视觉模型；图片与 OCR 内容属于不可信数据，不作为指令执行。

## 附件与路径边界

附件资源模块是 attachmentId、storageKey、原始文件名和会话归属的权威索引。产品会话记录只保存资源标识，不保存图片 base64。

支持图片的模型调用原生 Read 时，Runtime 工具输入需要真实绝对路径。路径只允许存在于当前运行内存和 Runtime 自身的续跑 checkpoint。

产品边界执行以下清理：

- Agent Trace 的 Read 输入只显示文件名。
- Zora 产品 JSONL 在持久化 Read 工具输入前，将已登记附件路径替换为 attachmentId 和文件名。Inspect Image 的 `path` 调用正常记录路径，本机路径不属于附件脱敏范围。
- 权限日志只记录文件名。
- 历史恢复提示不包含附件绝对路径。

图片、OCR 文本和文件正文统一视为用户提供的外部内容。固定系统提示要求模型将其中的指令和权限请求作为待分析数据，除非用户在对话中明确要求执行。

## 视觉模型请求

Inspect Image 接收：

- `attachmentId` 或 `path`，恰好提供一个
- 最多 1000 个字符的观察指令

中转服务负责：

1. 按 workspace、session 和 attachmentId 解析附件，或直接读取 `path` 指向的本机文件。
2. 校验图片格式、文件大小和像素限制。`path` 来源以文件头 sniff 结果为准，扩展名不参与判定。
3. 规范化图片后生成视觉模型请求。
4. 只发送规范化图片与单条观察指令。
5. 将视觉模型的文本结果封装为结构化 Observation 返回主模型。

视觉模型请求不包含完整对话历史、工作目录和原始附件路径。

`path` 分支的实现要求：

- 以 `O_NOFOLLOW` 打开文件，读到的 fd 做 inode 校验后交给解码，防止 TOCTOU 路径替换（Proma 已验证的模式）。
- 图片经 sharp 完整解码后重编码再外发，剥掉图片容器中夹带的任意字节。

## 超时与取消

30 秒只用于等待 HTTP 响应或流式首个响应。收到首个响应后取消该计时器，允许模型继续生成完整结果。

用户停止当前 Agent Run 时，通过同一 AbortSignal 取消视觉请求。首响应超时返回 `VISION_TIMEOUT`；用户取消返回 `VISION_CANCELLED`。二者不转换为通用网络错误。

## 设置界面

视觉助手页面保持两行：

1. 启用视觉中转。描述明示授权范围：开启后，Agent 会将本机图片（会话附件与本地路径）发送给所选视觉模型，结果只以文本返回。
2. 选择视觉模型。

开启开关时，如果当前没有选择模型，自动选择第一个已配置模型。没有已配置模型时禁用开关，并引导用户先完成模型配置。

模型选择变化即时保存。Provider、API Key、能力表、文件限制和内部协议不在视觉助手页面展示。

## 验收标准

- 支持图片的主模型读取图片时出现 Read，不出现 Inspect Image。
- 不支持图片或能力未知的主模型在视觉助手开启后出现 Inspect Image。
- 用户上传的图片附件走 `attachmentId` 调用 Inspect Image，Ask 权限模式下不弹出确认。
- 用户给出本机图片路径（或 Agent 通过文件工具发现、产出的图片）时，走 `path` 调用 Inspect Image，Ask 权限模式下不弹出确认，与 Read 行为一致。
- `path` 传入非图片文件（以文件头 sniff 判定）时返回 `VISION_UNSUPPORTED_IMAGE`，不发起视觉请求。
- `path` 不存在或不可读时返回 `VISION_FILE_NOT_AUTHORIZED`，不发起视觉请求。
- `attachmentId` 与 `path` 同时提供或都不提供时返回 `VISION_INPUT_INVALID`。
- 视觉助手关闭时不注册 Inspect Image，也不增加图片 Read 限制。
- 图片 Read 约束不影响文本和文档读取。
- 相同 modelId 只要任一 Pi Provider 目录记录支持图片，自动识别结果为 `supported`。
- 视觉模型首响应在 30 秒内到达后，完整生成超过 30 秒不会被中断。
- Agent Trace、产品 JSONL 和权限日志不包含已登记附件的绝对路径。
- 产品 JSONL 和历史恢复提示不包含图片 base64。
- 设置页可以选择任意已配置模型。
- 设置页启用开关的描述包含外发范围说明。

## 与 Proma 设计的对齐与差异

Proma 的 VisionRelay 是同一问题的先行实现，本设计吸收其验证过的部分，保留 Zora 已成立的差异。

采纳：

- 路径作为工具输入的一等接口。Proma 的 VisionRelay 只接受 `imagePath`，授权按目录范围（工作目录、项目文件目录、附加目录）判定。本设计的 `path` 输入源与其同构。
- 启用即授权的外发模式。Proma 在设置页明示开启即授权外发范围内图片，正常会话不逐次确认。本设计采用同一模式，授权点放在设置页。
- 结构化输出与最小外发。视觉模型只收图片与单条指令，返回结构化 JSON，不含对话历史。Zora 已实现同等约束。

不采纳：

- 硬编码模型适用范围。Proma 用正则限定 deepseek-v4 系列，Zora 的三态能力判定加用户覆盖是更通用的机制。
- 目录白名单作为唯一边界。Proma 完全自动放行，需要 allowedRoots 硬边界兜底。Zora 有会话权限模式体系，`path` 与 Read 同权即可，不额外建一层目录授权。
- 附件仅以路径文本投影。Proma 的 Agent 消息里附件是 `<attached_files>` 路径块。Zora 的 attachmentId 承担持久化与脱敏职责（JSONL 路径替换、fork 后附件重定向），保留 attachmentId 作为上传附件的规范引用，`path` 作为通用补充。
